# Database Schema

---

## What It Is

The foundational data structure of your entire application. Every feature, every query, every RLS policy builds on top of this. Getting the schema right early prevents painful migrations later. Getting it wrong means refactoring everything that touches data.

## Tenancy Model

**First question: does your product have the concept of teams, workspaces, or organizations?**

### Single-Tenant (user_id is the boundary)

If your product is per-user with no shared workspaces (personal tools, individual SaaS, solo-use products):

- Every table scopes data with `user_id` instead of `workspace_id`
- RLS policies check `user_id = authenticated_user` on every table
- Simpler schema, fewer tables (no workspace_members, no invitations, no roles)
- If you ever need teams later, retrofitting multi-tenancy onto a single-tenant schema is painful — so be honest about whether collaboration is on the roadmap

### Multi-Tenant (workspace_id is the boundary)

If your product has teams, workspaces, organizations, or any concept where multiple users share data:

- Use a shared database with a `workspace_id` column on every tenant-scoped table
- Data isolation is enforced by RLS policies, not application code
- Do not use separate schemas per tenant (over-engineered for MVP)
- Do not use separate databases per tenant (operational nightmare)
- The `workspace_id` column is the single most important column in your schema — it appears on almost every table and is the foundation of every RLS policy
- You need workspace_members (many-to-many with roles), invitations, and role-based RLS policies

**If in doubt, choose multi-tenant.** It's easier to have the structure and not use teams yet than to retrofit it later. A multi-tenant schema works fine for single users — a workspace with one member is just a personal workspace.

## Naming Conventions

- **Tables:** snake_case, plural nouns (`users`, `projects`, `workspace_members`)
- **Columns:** snake_case, descriptive, no abbreviations (`created_at` not `ca`, `year_founded` not `year`)
- **Primary keys:** `id` using `uuid` type, generated by default as `gen_random_uuid()`
- **Foreign keys:** `{referenced_table_singular}_id` (e.g., `workspace_id`, `user_id`, `project_id`)
- **Timestamps:** every table gets `created_at` and `updated_at` columns, both `timestamptz`, defaulting to `now()`
- **Booleans:** prefix with `is_` or `has_` (`is_active`, `has_verified_email`)
- **Indexes:** `idx_{table}_{column}` for regular indexes, `uniq_{table}_{column}` for unique constraints
- **RLS policies:** descriptive English names (`"Members can view workspace projects"`)
- **Enums:** use Postgres enums or text with check constraints, not integer codes. Values should be readable (`active`, `suspended`, `deleted` — not `1`, `2`, `3`)

## Data Types

- Use `uuid` for all primary keys and foreign keys — never auto-incrementing integers (they leak information about table size and creation order)
- Use `text` for strings — not `varchar`. Postgres treats them identically, and `text` doesn't require length decisions upfront
- Use `timestamptz` for all timestamps — always store in UTC, convert to local time in the frontend
- Use `jsonb` sparingly — only for truly unstructured data (user preferences, metadata). If you're querying into it regularly, it should be its own column or table
- Use `boolean` for true/false — not integer 0/1
- Use `numeric` for money — never `float` or `double precision` (floating point errors on currency will burn you)

## updated_at Auto-Update

Every table has an `updated_at` column, but it does not update itself. You must set up an auto-update mechanism.

- Create a database trigger function that sets `updated_at = now()` on every UPDATE operation
- Apply this trigger to every table that has an `updated_at` column
- This is a one-time setup — define the function once, attach the trigger to each table in its migration
- Do not rely on the application to set `updated_at` — it will be forgotten in at least one place, and your timestamps will go stale

## Column Ownership Classification

Every column in every table should be classified by who/what is allowed to write to it. This determines RLS UPDATE policies and prevents bugs where user input overwrites system-managed fields.

- **USER** — editable by the authenticated user via the frontend (e.g., profile name, settings, preferences). RLS UPDATE policies should restrict to only these columns.
- **SYSTEM** — written by backend/server code only (e.g., created_at, stripe_customer_id, usage counters). Never accept these values from client requests. System context only.
- **ADMIN** — writable only by admin users or admin tooling (e.g., subscription plan definitions, feature flags, taxonomy data). Typically managed via an admin dashboard or direct database access.

When designing a table, tag every column with its ownership. This prevents the common mistake of an RLS UPDATE policy that allows users to modify system-managed fields like plan, credits_used, or stripe_subscription_id.

## Table Creation Order

Tables with foreign key dependencies must be created in the correct sequence. When writing migrations, always create referenced tables before the tables that reference them.

Document the dependency order as part of your schema. A table that references workspaces, profiles, and subscription_plans cannot be created until all three exist. When in doubt, draw the dependency graph and create from the roots outward.

## Core Table Patterns

Every SaaS needs these foundational table patterns. The actual columns will vary by product, but the structure is consistent.

### Profiles (extends auth users)
- Your auth provider manages the users table (do not duplicate auth fields)
- Create a separate profiles table that references the auth user's ID and holds app-specific data (display name, avatar, settings)
- This is the only table where the primary key directly references the auth user. All other tables reference profiles.

### Workspaces (multi-tenant only)
- Every workspace gets a unique slug for URLs
- Stripe references (customer_id, subscription_id) live here — one billing relationship per workspace
- The current plan name is synced from Stripe webhooks and stored locally for quick access

### Workspace Members (multi-tenant only)
- Many-to-many with a role column (owner, admin, member, viewer)
- Unique constraint on (workspace_id, user_id) — a user cannot be a member twice
- Roles are per-workspace, not global

### Invitations (multi-tenant only)
- Store the invited email (which may not be an existing user yet), role, token, and expiry
- Token is unique and expires after 7 days
- Track accepted_at to know which invitations were used

### Feature Tables
- Every feature table follows the same pattern: id, tenant boundary (workspace_id for multi-tenant or user_id for single-tenant), created_by, feature-specific columns, created_at, updated_at
- The tenant boundary column is what makes RLS work. Never create a feature table without it unless the data is truly global.
- The created_by column links to profiles and tracks who created the record. Set it server-side from the session, never from the client. In single-tenant, created_by and user_id will be the same — include both anyway for consistency.

## Client Context Rules

Every database operation runs in one of two contexts, determined by the column ownership:

- **User context (RLS enforced):** all user-facing reads and writes on USER columns. The request carries the user's identity and RLS policies determine what data they can see and modify.
- **System context (elevated access, bypasses RLS):** backend operations on SYSTEM and ADMIN columns — webhook handlers, cron jobs, background workers, admin operations, data migrations.

This is a hard rule. If you need to update a SYSTEM column (like incrementing a usage counter or syncing a Stripe subscription ID), that must go through a server action or backend function running in system context. Never accept SYSTEM column values from user-facing requests.

## Billing Tables

Do not replicate Stripe's data model in your database. Stripe is the source of truth for billing.

**Store locally (on the workspaces table):**
- stripe_customer_id — links your workspace to a Stripe customer
- stripe_subscription_id — links to the current subscription
- plan — current plan name, synced from Stripe webhooks

**Do NOT store locally:**
- Invoice details, payment history, payment method details, price amounts — query Stripe's API when needed. Stripe handles PCI compliance and retains all billing history.

**Webhook deduplication:**
- Create a webhook events table with a unique constraint on the provider's event ID (e.g., Stripe's event ID)
- Before processing any webhook, check if the event has already been processed. This prevents duplicate charges, duplicate emails, and duplicate state changes.
- Store: event_id (unique), event_type, processed_at, processing_error, retry_count

**Usage/credit tracking (if applicable):**
- Track usage per workspace per billing period (workspace_id, period_start, period_end, credits_used, credits_limit)
- Check against limit before allowing actions
- Reset on billing period change (triggered by Stripe webhook)

## Audit Logging

For subscription changes, payment events, and sensitive operations, maintain an immutable audit log.

- Store: table_name, record_id, action (INSERT/UPDATE/DELETE), old_values (jsonb), new_values (jsonb), changed_by (user or system identifier), timestamp
- Audit logs are immutable — no UPDATE or DELETE allowed
- Typically populated by database triggers, not application code (ensures nothing is missed)
- RLS: only admin users can read audit logs

## Soft Deletes vs Hard Deletes

Use soft deletes for user-facing data that might need recovery. Use hard deletes for ephemeral data.

**Soft delete** (add `deleted_at` timestamptz, nullable):
- Workspaces, projects, user-generated content, team members
- Null means active, non-null means deleted
- Every RLS SELECT policy on soft-deletable tables must include `AND deleted_at IS NULL` — this ensures deleted data is invisible to users without additional application logic
- Purge soft-deleted records after 30 days with a scheduled job

**Hard delete:**
- Sessions, expired invitation tokens, temporary upload records, processed webhook events older than 90 days

## State Machine Documentation

Tables with status/state columns (e.g., subscription status, order status) should have their valid state transitions documented. This prevents AI from building code that allows invalid transitions.

For example, a subscription should not go from "cancelled" to "active" — a cancelled subscription's lifecycle is over, and reactivation creates a new record. Document these rules alongside the table design so the implementation enforces them.

## File Storage Design

If your product handles file uploads (images, documents, etc.), design your storage alongside your schema.

**Bucket strategy:**
- Separate buckets for different access patterns (public assets vs private user uploads)
- Public buckets for content that can be accessed via direct URL (logos, published images)
- Private buckets for user-specific content that requires authentication

**Path-based isolation:**
- File paths must include the workspace_id and user_id: `{workspace_id}/{user_id}/{filename}`
- RLS on storage validates that the path matches the authenticated user's workspace membership
- Prevents path manipulation attacks (user cannot access another workspace's files)

**Temporary vs permanent storage:**
- Flag temporary uploads (is_temporary boolean) for automatic cleanup
- Scheduled cleanup job deletes temporary files after their retention period
- Files promoted to permanent (e.g., user confirms upload) have the flag cleared

## Indexing Strategy

Index the columns you query by. Do not index everything preemptively.

**Always index:**
- `workspace_id` on every feature table (every query filters by workspace)
- Foreign keys that are used in joins
- Columns used in `WHERE` clauses frequently (e.g., `email`, `slug`, `status`)
- Columns used in `ORDER BY` with large result sets (`created_at`)

**Composite indexes:**
- If you always query `WHERE workspace_id = X AND status = Y`, create a composite index on `(workspace_id, status)`
- Column order matters — put the most selective column first

**Do not index:**
- Boolean columns (low cardinality, index won't help)
- Columns only used in `SELECT` (not `WHERE`, `JOIN`, or `ORDER BY`)
- Tables with fewer than a few thousand rows (full scan is faster than index lookup)

**Monitor before optimizing:**
- Use `EXPLAIN ANALYZE` on slow queries to verify whether an index would help
- Use your database provider's query performance dashboard or `pg_stat_statements` to identify slow queries

## Migration Strategy

Schema changes are tracked as versioned migration files, regardless of tooling.

- Migration files are timestamped and sequential: `20260406120000_add_projects_table.sql`
- Migrations always roll forward — never modify a deployed migration. If you need to undo something, create a new migration that reverts the change.
- Test migrations locally before deploying to any shared environment

**Environment flow:**
- Write migration → test locally → deploy to staging → verify → deploy to production
- Never apply migrations directly to production without testing on staging first

## RLS Policy Design

RLS policies are defined per table, per operation (SELECT, INSERT, UPDATE, DELETE). They run on every query automatically.

**Design principles:**
- Default deny: enable RLS on every table, then add explicit allow policies
- Every policy references the authenticated user via the current session's user ID function
- Workspace-scoped tables check membership: "user is a member of this workspace"
- Role-restricted operations add role checks: "user is admin or owner in this workspace"
- Use security definer functions for complex checks to avoid repeating subqueries across policies

**UPDATE policies must restrict columns:**
- RLS UPDATE policies should only allow modifications to USER-classified columns
- SYSTEM and ADMIN columns must not be updatable through the browser client
- Document the allowed columns for each table's UPDATE policy

**Soft delete integration:**
- Every SELECT policy on soft-deletable tables must include `AND deleted_at IS NULL`
- This makes soft-deleted records invisible at the database level, not just the application level

**Common policy patterns:**
- **Own data only:** row's user_id matches the authenticated user
- **Workspace member:** row's workspace_id is in the set of workspaces the authenticated user belongs to
- **Workspace admin:** same as workspace member, plus the user's role in that workspace is admin or owner
- **Insert with ownership:** created_by must match the authenticated user AND workspace_id must be one they belong to

## What to Test

- RLS policies block cross-workspace data access (user in workspace A cannot read workspace B's data)
- RLS policies enforce column-level UPDATE restrictions (user cannot modify SYSTEM columns)
- Soft-deleted records are invisible through RLS SELECT policies
- Foreign key cascades work correctly (ON DELETE CASCADE, ON DELETE SET NULL)
- updated_at trigger fires on every UPDATE
- Unique constraints prevent duplicates (workspace slug, workspace member)
- Webhook deduplication table rejects duplicate event IDs
- Multi-tenant queries never return data from other workspaces

## Edge Cases

- **User belongs to multiple workspaces** — every query must be scoped to a specific workspace_id, typically derived from the URL or a workspace switcher in the UI. Never query across workspaces unless you're building admin tooling.
- **Workspace owner leaves** — ownership must be transferred before the owner can leave or delete their account. Block the action if they're the sole owner.
- **Slug collision** — workspace slugs must be unique. Check availability before creation and handle the race condition (unique constraint will catch it, surface a friendly error).
- **Cascade deletes** — when a workspace is deleted, all its data must be cleaned up. Use `ON DELETE CASCADE` on foreign keys for hard-deleted tables, and a soft-delete cascade function for soft-deleted tables.
- **Timezone confusion** — all timestamps are `timestamptz` stored in UTC. The frontend converts to local time for display. Never store local times in the database.
- **Null vs empty string** — use `NULL` for "no value provided", never empty string. Enforce with check constraints where appropriate.
- **Orphaned records** — if a user is deleted but their content is anonymized in shared workspaces, ensure foreign keys use `ON DELETE SET NULL` for the `created_by` column on shared content tables.
- **Migration on production data** — adding a `NOT NULL` column to a table with existing rows requires a default value. Always include `DEFAULT` when adding non-nullable columns to existing tables.
- **RLS policy blocks admin operations** — system context bypasses RLS. Server-side admin operations (migrations, bulk updates, cleanup jobs) must run in system context, never user context.
- **Webhook processed twice** — without a deduplication table, a retried webhook from Stripe can double-charge a customer or send duplicate emails. Always check the event ID against the webhook events table before processing.
- **Subscription status conflicts** — a cancelled subscription record is end-of-lifecycle. Reactivation must create a new subscription record, not update the old one. Document valid state transitions for every status column.
- **User updates system column via API** — if your RLS UPDATE policy is too permissive, a user could modify their own plan, credits, or Stripe IDs. Column ownership classification and restricted UPDATE policies prevent this.
- **Concurrent writes to the same row** — two users update the same record simultaneously. Use `updated_at` as an optimistic lock — check that it hasn't changed since the read before applying the update.
- **Foreign key references deleted record** — decide ON DELETE behavior for every foreign key at design time: CASCADE (delete children), SET NULL (keep children, clear reference), or RESTRICT (block deletion if children exist).

## Common Mistakes

- Auto-incrementing integer IDs (leaks information, causes issues with distributed systems)
- Storing timestamps without timezone (leads to timezone bugs that are nearly impossible to debug)
- Duplicating Stripe's data model locally (you'll fight sync issues forever — let Stripe be the source of truth)
- Missing workspace_id on a feature table (breaks multi-tenancy, data leaks between tenants)
- Not enabling RLS on a new table (one forgotten table = full data exposure)
- RLS UPDATE policy too permissive (user can modify system columns like plan or credits)
- Using jsonb for structured data you query regularly (use proper columns — jsonb is for genuinely unstructured data)
- Not indexing workspace_id (every query filters by it — without an index, every query scans the full table)
- Modifying deployed migrations instead of creating new ones (breaks other environments)
- Applying migrations directly to production without testing on staging
- Using `float` for money (0.1 + 0.2 ≠ 0.3 in floating point)
- Forgetting `ON DELETE CASCADE` or `ON DELETE SET NULL` on foreign keys (orphaned records accumulate silently)
- No webhook deduplication (retried webhooks cause double-processing)
- Allowing invalid state transitions (cancelled → active instead of creating a new record)
- Accepting user IDs or system values from client requests instead of deriving them server-side
- No updated_at trigger (column exists but never gets updated, timestamps go stale)
- Validating only at application level without database check constraints (bypassed by direct access or bugs)
- Validating only at database level without Zod (user gets cryptic Postgres errors instead of friendly messages)
